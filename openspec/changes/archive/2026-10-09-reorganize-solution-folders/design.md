## Context

See `proposal.md` for motivation. `AgentMesh.sln` currently contains fourteen root-relative project entries: thirteen production or executable projects and `AgentMesh.Infrastructure.Responses.Tests`, the single test project. Inter-project `ProjectReference` values are currently sibling-relative. `src/AgentMeshWeb/Dockerfile` uses repository-root build-context paths for `COPY`; its restore and publish commands operate on the copied project under `/src/AgentMeshWeb`. The README uses repository-relative `dotnet` and Docker commands. The configured architecture baseline path is absent, so this design is grounded in the current solution, project files, README, and available archived architecture documentation.

## Goals / Non-Goals

**Goals:**
- Establish `src/` as the home of all non-test solution projects and `tests/` as the home of all test projects.
- Preserve repository-root ownership of solution and repository metadata files.
- Ensure every build, test, packaging, container, documentation, CI, and OpenSpec path resolves from its documented working directory after the move.

**Non-Goals:**
- Introduce solution folders in Visual Studio, rename projects, or change the project dependency graph.
- Relocate generated `bin/` or `obj/` content independently; it moves with each project and is regenerated by normal builds.

## Decisions

### Move whole project directories by project classification

- **Choice:** Move the thirteen non-test project directories to `src/<existing-project-name>/` and move `AgentMesh.Infrastructure.Responses.Tests` to `tests/AgentMesh.Infrastructure.Responses.Tests/`.
- **Rationale:** Moving whole directories preserves source-relative content includes, project metadata, and local configuration without piecemeal rewrites. Classifying by `IsTestProject` keeps the test boundary explicit.
- **Alternatives considered:** Moving only `.csproj` files would separate project metadata from source and break conventional SDK project discovery. Keeping test projects in `src/` would not satisfy the requested layout.

### Retain the repository root as the command and metadata anchor

- **Choice:** Keep `AgentMesh.sln`, `NuGet.config`, root README, `.github`, and `openspec` at the root; update solution entries to `src/...` or `tests/...` and continue running root-context commands from there.
- **Rationale:** NuGet configuration lookup and Docker build contexts already assume the root is the repository boundary, while source/test classification is expressed by the new child directories.
- **Alternatives considered:** Moving the solution or NuGet configuration would expand scope and force a new command anchor without a layout benefit.

### Recalculate only cross-boundary relative project references

- **Choice:** Preserve sibling-relative `ProjectReference` paths among relocated `src` projects, and change test-to-source references to traverse from `tests` to `src`.
- **Rationale:** A uniform `src` move retains most existing reference relationships and minimizes edits. The Responses test project is the known cross-boundary case.
- **Alternatives considered:** Replacing project references with package references would alter development and restore behavior outside scope.

### Treat documented and operational paths as migration surface

- **Choice:** Update tracked path references in solution metadata, project files, Dockerfiles/templates, CI configuration, READMEs, and current OpenSpec artifacts that present runnable source-tree commands or canonical file paths; exclude stale generated outputs under `bin/` and `obj/`, and preserve archived artifacts as historical records.
- **Rationale:** Docker build instructions already require root-context paths and will fail if they retain the old project-root paths after the move. Documentation and OpenSpec are developer-facing contracts for repository navigation.
- **Alternatives considered:** Updating only build files leaves false instructions and future planning references behind.

## Risks / Trade-offs

- **[Risk]** A missed relative path can surface only in a specific build, test, pack, or Docker invocation. **Mitigation:** Search active tracked files for every old root-level project directory and validate the solution build, test project, package commands, and Docker build.
- **[Risk]** Broad text replacement can alter namespaces or package names that intentionally retain project identifiers. **Mitigation:** Limit replacements to path-bearing syntax and review the final diff for semantic identifier changes.
- **[Trade-off]** Existing external links that point to old repository paths will break. **Mitigation:** Update in-repository documentation and OpenSpec references; external consumers must use the repository revision they target.

## Migration Plan

1. Inventory source and test projects from the solution, then move each complete project directory to its target root.
2. Update `AgentMesh.sln` and every affected `ProjectReference` using the new relative locations.
3. Update root-context Dockerfiles/templates, CI configuration, README commands, and OpenSpec file-path references while leaving root metadata in place.
4. Search tracked files for obsolete root-level project paths, then build the solution, run the relocated test project, package the documented projects, and build the Web Docker image from the root.
5. Roll back by restoring the directory moves and the associated path-only edits together; no data or runtime migration is required.
